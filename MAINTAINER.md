# Maintaining Semolina

## Prerequisites

1. [Install uv](https://docs.astral.sh/uv/getting-started/installation/) — **0.9.18 or
   newer**. That floor is not cosmetic: `pyproject.toml` requires `uv_build>=0.9.18`, the
   `uv-pre-commit` hook is pinned to the same release, and older uv ships a Python index
   that resolves this repo's `.python-version` (`3.14`) to a release candidate rather than
   the stable build. On 3.14.0rc2 the locked pydantic raises
   `TypeError: _eval_type() got an unexpected keyword argument 'prefer_fwd_module'` at
   import, so nothing collects — that is the toolchain being out of date, not the project
   being broken.
2. [Install prek](https://prek.j178.dev/installation/) (runs the pre-commit hooks).
3. [Install just](https://just.systems/man/en/) (task runner; `just --list` shows everything).

## Quality gates

Run all three before committing.

| Command | What it covers | Also enforced in CI? |
|---------|----------------|----------------------|
| `prek run --all-files` | ruff lint + format, basedpyright strict (and standard over the jaffle-shop example), shellcheck, uv lockfile, blacken-docs, JSON/TOML/YAML syntax | Partly — CI runs ruff check, ruff format and basedpyright (both passes) as their own jobs. Nothing in CI runs shellcheck, `uv lock --check`, blacken-docs or the whitespace hooks, so those are local-only and a hook you skip is not caught later |
| `just test` | unit + doctest + cassette-replay suite, then the jaffle-shop workspace member | Yes, across Python 3.11-3.15, plus coverage |
| `just docs-build` | Sphinx in strict mode (`-W`, plus `nitpicky = True` in `conf.py`) | Yes, on every push and PR |

`just test` starts with `uv sync --locked --dev --extra all`, and that step is what makes
the run mean anything. A plain `uv sync --dev` installs none of the `duckdb`, `snowflake`,
`polars`, `pandas` or `arrowmodel` extras, and roughly fifty test files then
`pytest.importorskip` their way to a green run over a much smaller suite than CI executes.
If your local skip count is far above CI's, the sync is the first thing to check.

The suite runs in two passes, in `just test` and in CI alike. Everything except the
`timing` tests runs under `-n auto`; the `timing` tests, which compare a cancelled query's
elapsed time against an uncancelled baseline, run afterwards on their own, so a runner
busy with other workers cannot skew one measurement against the other. A plain
`pytest -n auto` still runs them in parallel and can be noisy there.

Coverage is measured in CI only, with a `fail_under` floor in `[tool.coverage.report]`. The
first pass turns the floor off, so it is checked once, on the combined data. To reproduce that
locally:

```sh
uv run pytest --cov=src/semolina --cov-report= --cov-fail-under=0 -n auto -m "not timing"
uv run pytest --cov=src/semolina --cov-append --cov-report=term-missing -m timing
```

## Recording warehouse cassettes

The integration tests replay committed ADBC cassettes and need no credentials. Re-recording
does need a live warehouse and is a local, credentialed step:

```sh
uv run pytest --adbc-record=once tests/integration
```

The jaffle-shop workspace member runs against DuckDB only (its Snowflake tests were removed in
favour of the recorded cassettes above), so CI runs that suite unfiltered.

## Releasing

Version is static in `pyproject.toml`; the tag must agree with it.

1. Bump `project.version` in `pyproject.toml`, and land it on `main` with CI green.
2. Tag the release commit and push the tag:

   ```sh
   git tag v0.7.0
   git push origin v0.7.0
   ```

3. `release.yml` then runs, in this order:
   - **version-gate** — refuses the tag unless it matches `project.version`, compared as
     PEP 440 versions so `v0.7.0-rc1` matches `0.7.0rc1`. Runs before anything is built.
   - **ci** — the whole CI workflow against the tagged commit. `ci.yml` ignores tag pushes,
     so this call is the only thing that tests what is about to ship.
   - **build** → **validate** → **changelog** → **publish** → **github-release**. Publishing
     waits on `ci`, and `validate` additionally asserts the built wheel reports the tagged
     version at runtime.

Publishing uses PyPI trusted publishing via the `pypi` environment; no API token is stored
in the repo. The changelog is generated by git-cliff from conventional commits and is
attached to the GitHub release.

Note that `0.3.0`, `0.4.0` and `0.6.0` reached PyPI before any of this existed — they were
published outside `release.yml`, which is why the repository carries no tags for them and
why the workflow's first real run will be the next release.
