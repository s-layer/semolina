**Generated:** 2026-11-20 (0.10.0 documentation gate, update mode, pass 1)
**Audience:** Data engineers exposing semantic layers via APIs (intermediate)
**Scenarios tested:** 6 (S1-S5 reused from `scenarios.yaml`, since no pages were added or

**Results:** 5 PASS, 1 PARTIAL, 0 FAIL

## Summary

This persona reaches the 0.10.0 changes through codegen and local DuckDB work. All of them
are documented, and every claim checked against source holds. The models guide's metadata
table now has DuckDB rows for tags. The `--check` page and the changelog explain when a
hand-added `label=` becomes drift and why a model generated by an earlier release does. The
streaming guide and the changelog cover polars 2. The remaining friction is DuckDB-local
(S4). The tag and fact behaviour now depends on which `semantic_views` build DuckDB has
cached, and no page says how to see or update that build. The Fact section of the models
guide still describes every DuckDB fact query as `facts :=` plus `SELECT DISTINCT`, which
0.10.0 made true only for a query that selects nothing but facts.

Source checks run for this pass (outside the doc-only simulation, as the caller asked):
a DuckDB view tagged `S_LAYER_LABEL`, lowercase `s_layer_kind` and `S_LAYER_SPEC` generated
`label=` and `semantic_format=` as documented. A hand-added `label=` on an untagged fact
gave `Detail: unit_price: label: committed 'Unit price', warehouse None` and exit `5`. A
facts-with-dimensions query sent `dimensions := ['country', 'unit_price']` with no
`DISTINCT` and returned grouped rows on extension v0.19.0. `adbc-poolhouse` 1.8.1 requires
`adbc-driver-manager>=1.13.0`, and both the base and the `async` floors are 1.8.1 in
`pyproject.toml`.

## Scenario S4: What works on local DuckDB

**Verdict:** PARTIAL

### Navigation Path

1. `index.rst` > "Configure your warehouse backend" > `how-to/backends.rst` > DuckDB >
   The semantic_views extension
   - Found: `create_engine` runs `INSTALL`/`LOAD`, "`INSTALL` is a no-op once the extension
     is cached locally", and the extra pins DuckDB.
   - Friction: unlike the Databricks section, the DuckDB section has no "generate a model"
     paragraph, so nothing here says codegen reads comments, synonyms or tags. Found by
     going to the codegen guide instead.
2. `how-to/codegen.rst` > Understand the generated output > DuckDB tab, then the metadata
   paragraph > `how-to/models.rst` > Where the warehouse holds them
   - Found: DuckDB now reads `S_LAYER_LABEL`, `S_LAYER_KIND`, `S_LAYER_SPEC` from the
     `TAGS` row; needs `semantic_views` 0.17.0; case-insensitive and qualified tag names;
     an earlier extension leaves hand-added arguments alone.
   - Friction: the page says *which* version I need but not which one I *have*. The extra
     pins DuckDB 2.0.0, not the extension, and step 1 says a cached build is never
     refreshed. So a laptop that cached 0.16 in October and a fresh CI runner on 0.19+ can
     disagree about whether a hand-added `label=` is drift. No page shows how to read the
     loaded version (`SELECT extension_version FROM duckdb_extensions() WHERE
     extension_name = 'semantic_views'`, the same query Semolina runs) or how to move a
     cached build forward (`UPDATE EXTENSIONS (semantic_views)`). `how-to/queries.rst`
     says the pinned DuckDB 2.0.0 "installs" 0.16.0 for grains. No page makes the
     matching statement for 0.17.0 and tags.
   - Friction: the changelog says "move it into the view's tags", but no page shows DuckDB
     tag DDL. A data engineer hand-building a local fixture to mirror a dbt-s-layer-tagged
     Snowflake view has no example of `WITH TAG (S_LAYER_LABEL = '...')` on a member, or of
     what `S_LAYER_SPEC` holds. (Measured: `S_LAYER_SPEC='{"currency_code":"USD"}'` is
     refused with `currency_code: unknown key`; `'{"value":{"currency":"USD"}}'` is the
     accepted shape. A reader has to guess this.)
3. `explanation/duckdb-vs-warehouse.rst` > Fact queries return the same rows
   - Found: the new paragraph explains that from extension 0.18.0 a facts-plus-dimensions
     call is refused, so Semolina lists the facts under `dimensions` and gets the
     `GROUP BY ALL` rows. Clear, and it matches the SQL Semolina sends.
4. `how-to/models.rst` > the Fact section (above "Type the subscript"), reached from the
   models guide while reading about field types
   - Friction: still says "DuckDB's `semantic_view()` takes facts in their own `facts :=`
     argument and returns them row by row, so Semolina adds `SELECT DISTINCT` to a fact
     query there". Since 0.10.0 that holds only for a query selecting facts alone; a fact
     selected beside a dimension goes in `dimensions :=` with no `DISTINCT`. The page
     doesn't link to the explanation that says so. This is the page a model author reads,
     and the one the release didn't touch.
5. `how-to/queries.rst` > grain DuckDB tab: grains need 0.16.0, the extra installs it.
   Unchanged.

### Gap Analysis

**Where:** `how-to/models.rst` > Where the warehouse holds them (the DuckDB paragraph),
and/or `how-to/codegen.rst` > Read the Detail lines
**What:** The docs state the 0.17.0 requirement but give no way to see the loaded
extension version or refresh a cached one. `INSTALL` never upgrades a cached build, so
local and CI runs can disagree.
**Impact:** `--check` can pass locally and fail in CI (or the reverse) on the same model,
with no doc explaining why.
**Suggested Fix:** In `how-to/models.rst`, DuckDB paragraph: add two sentences. "Semolina
uses the version loaded on the codegen connection. Check it with `SELECT extension_version
FROM duckdb_extensions() WHERE extension_name = 'semantic_views'`, and run `UPDATE
EXTENSIONS (semantic_views)` to replace an older cached build, so CI and your laptop
agree." Optionally say the pinned DuckDB 2.0.0 gets 0.17.0 or later on a fresh install, as
`queries.rst` does for 0.16.0.

**Where:** `how-to/models.rst` > the Fact section, paragraph beginning "On Snowflake and
Databricks, `Fact` and `Dimension` produce identical SQL"
**What:** Describes every DuckDB fact query as `facts :=` plus `SELECT DISTINCT`. Since
0.10.0 that is only the facts-only case.
**Impact:** A reader comparing `.to_sql(dialect="duckdb")` output for a facts-and-dimensions
query against this page sees SQL the page says won't happen.
**Suggested Fix:** In `how-to/models.rst`, section on `Fact`: change "to a fact query
there" to "to a query that selects only facts there", and add: "A query that selects facts
beside dimensions lists the facts under `dimensions :=` instead, which groups on them (see
`explanation-duckdb-vs-warehouse`)."

**Where:** `how-to/models.rst` > Where the warehouse holds them (DuckDB paragraph)
**What:** No example of a tagged DuckDB member, though the changelog tells readers to
"move it into the view's tags".
**Impact:** A hand-written local fixture can't be tagged without leaving the docs; the
`S_LAYER_SPEC` shape has to be guessed.
**Suggested Fix:** Add a short `CREATE SEMANTIC VIEW` snippet with one metric carrying
`WITH TAG (S_LAYER_LABEL = 'Revenue', S_LAYER_KIND = 'currency', S_LAYER_SPEC =
'{"value": {"currency": "USD"}}')` and the generated field, or link to where the S-LAYER
block format is documented.

**Where:** `how-to/backends.rst` > DuckDB (pre-existing)
**What:** No "generate a model" paragraph to match the Databricks one added at 0.9.1.
**Suggested Fix:** Add one sentence under The semantic_views extension (or a short
subsection): codegen reads each member's `COMMENT`, `WITH SYNONYMS` and, from extension
0.17.0, its `S_LAYER_*` tags, linking `howto-models-metadata`.

## Open question for the author (not a doc gap)

`explanation/duckdb-vs-warehouse.rst` and the changelog say the extension refuses
facts-with-dimensions "from version 0.18.0". Semolina 0.10.0 now sends facts under
`dimensions :=` on every extension version (`DuckDBSQLBuilder` has no version gate). I
confirmed this works on v0.19.0. I could not confirm that 0.16.x or 0.17.x accepts a fact
named in `dimensions`. The extension's 0.18.0 changelog lists "A fact listed in
`DIMENSIONS` is grouped on" under its own changes, which suggests it might not. If older
builds refuse it, readers with an older cached build would see 0.10.0 break a query that
0.9.1 ran, and the docs should say the fix needs 0.18.0 or later.

Also noted, not a gap: from 0.18.0 the extension accepts a fact in `dimensions` beside
metrics, so DuckDB's facts-and-metrics `ValueError` could in principle be lifted the same
way. The docs correctly describe current behaviour.
